# Qwen3-VL-2B-Instruct：候选视觉核验离线测试

2026-10-27。结论：对本批复合条件误报有明显帮助，但 2B 模型尚不足以稳定判断“未佩戴安全帽”；耗时显著高于现有向量检索。本次不建议直接默认接入正式页面。

## 配置与来源

- 官方 [Qwen3-VL-2B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-2B-Instruct)，固定 revision `89644892e4d85e24eaac8bacfd4f463576704203`。
- Transformers 4.57.6、PyTorch 2.8.0、MPS、FP16、SDPA；Apple M5 / 32 GiB。
- 视频按片段均匀抽 16 帧，每帧最多 65,536 像素，约 1,048,576 总像素上限；补测提高至每帧 131,072、总计 2,097,152。实际尺寸见每条 `video_grid_thw`。
- 依照 [官方 Qwen3-VL 用法](https://github.com/QwenLM/Qwen3-VL) 传入视频元数据，patch size=16，视觉工具处理后 `do_resize=False`；不传文件名、样本标签或媒体 ID 给模型。
- 固定中文核验提示，输出 JSON match=yes/no/unknown 和短画面依据，greedy decoding，max_new_tokens=96。不把文字自报置信度当分数。
- 模型文件约 4.26 GB，首次下载约 7 分 49 秒；下载不计入查询耗时。
- 37 个主测试项、15 个针对性补测项，另重复核验同一组前 5 候选两次。多项复用同一素材，不是 52 个独立视频。

## 复合条件与正确结果

| 内容 | 当前正式结果 | 主测试核验后 | 说明 |
| --- | ---: | ---: | --- |
| 有人在户外慢跑 | 5 | 0 | 其中 4 个已人工标为不匹配，另 1 个未作确定标注；模型拒绝全部 5 个 |
| 戴红色安全帽的人骑自行车 | 3 | 0 | 3 个已标记误报全部拒绝 |
| 戴红色安全帽的人坐着写字 | 1 | 0 | 误删正确片段，把坐着写字者的帽子看错 |
| 室内慢跑、炒蔬菜、仓库摔倒、火情 | 各 1 个指定正确片段 | 全保留 | 这四项为已知正确片段对照，不是各自全量检索准确率 |

主测试中，复合条件的 7 个已标记误报全部剔除，5 个指定正确片段保留 4 个；不能仅凭拒绝误报宣称整体准确率提升到 100%。

对被误删的写字片段加倍像素预算后，模型判断改为 yes，约 13.06 秒；原低预算约 8.26 秒。这是单例补测，不能推断加分辨率可修复所有问题。

## 未佩戴安全帽

### 有帮助的部分

- 5 个固定视频：2 个裸头片段判 yes，3 个戴帽片段判 no，结论均符合标签。但两个裸头片段来自同一仓库素材，且有一项解释与结论矛盾。
- 6 张人物头部局部图片：3 个戴帽、3 个裸头，结论全部正确。它们来自仅 3 张照片，且已经人工裁好头部，只能说明清晰局部输入的可行性，不能替代真实视频检索指标。
- 实际摘帽后的片段能判 yes；已知仓库裸头片段 17 的 16–24 秒也能判 yes。

### 尚不能稳定满足的部分

1. **小头部误判**：严格摘帽前的 0–4 秒，两个人都戴红色安全帽，低预算却判 yes，声称坐着的人裸头。提高像素预算后改为正确 no。
2. **不可见被当作未戴**：`head-out-of-frame.jpg` 只有躯干、手和桌面，头部完全不在画面内，预期应为 unknown；模型却判 yes，并声称“头部清晰裸露”。因此目前不能把“看不见帽子”可靠转化为“确认没戴帽子”。
3. **结论与依据矛盾**：部分输出 match=no，但 evidence 写“头部裸露、未佩戴安全帽”；另有左右人物归属错误。例子保留在原始回答和 `review.json`，不能因为最终枚举碰巧正确就忽视这些问题。
4. **召回位置问题**：现有正式查询“作业人员没有佩戴安全帽”返回视频 27、30、21。已知仓库裸头在视频 17 的 16–24 秒，原始片段排序第 16 名、分数约 0.498，被现有门槛过滤掉；按视频最佳片段又会选择视频 17 的 0–8 秒。Instruct 只能核验送入的片段，不能自动补回漏掉的视频或时间段。后续若接入，要单独验证更宽的片段候选池，而不是仅核验当前每视频一个结果。

### 标注修正

原设计误把视频 27 的 0–6 秒标为完全摘帽前。逐帧核对发现，约 4.77–5.17 秒已经摘帽，因此这段应为 yes；保留 `design-original.json`、原始回答，并在 `design.json` 中修正标签。另新增严格 0–4 秒作为阴性补测。证据见 `hat-before-review.jpg`。补测没有修改原始模型输出。

### 结构化观察对照

针对否定语义与结论矛盾，补测了“只输出作业场景和 helmet/bare/unclear 状态，再由代码判断”的提示，8 个安全帽视频重复验证。

- 8 次都把要求的 heads 数组输出成字符串，严格格式校验全部不通过。
- 离线仅做封闭枚举的格式归一化（例如 `"helmet,bare"` → `["helmet","bare"]`，不改观察内容）后，只有 4/8 判断正确。
- 这是看到首轮问题后的诊断性提示尝试，不是独立测试集调参成功，也不能证明结构化输出方案普遍更差；本次没有证据表明它能稳定修复此模型的问题。

## 性能成本

以下为本机实际运行环境，正式 Embedding/OWLv2/人脸服务保持运行；系统有较多交换内存，不能外推至其他机器或推理后端。每条计时包含抽帧、预处理和生成，不包含模型加载。

| 项目 | 实测 |
| --- | ---: |
| Instruct 模型加载，两次进程 | 59.50 秒、39.45 秒 |
| 加载后首次预热推理 | 14.43 秒、11.86 秒 |
| 主测试单视频热核验 | 4.47–13.41 秒，中位数 9.33 秒 |
| 前 5 候选连续核验，三轮 | 45.20 / 56.46 / 45.63 秒 |
| 前 10 候选连续核验，一轮 | 98.96 秒 |
| 高预算摘帽前 0–4 秒 | 13.39 秒，低预算为 5.82 秒 |
| 高预算补测视频范围 | 10.99–18.05 秒（5 个样例） |

这意味着按当前实现，在现有检索后追加 5 个候选核验，通常要再等待约 45–56 秒；10 个约增加 99 秒。现有接口本次采样约 0.004–1.53 秒（包含重复查询缓存），不可把缓存查询与新查询混为一谈，也不建议用夸张倍数表达差异。

同一组 5 个候选三轮分类结果一致，但运行时间有波动。核验结果未缓存；正式实现若缓存会改善重复查询，不代表新查询也同样快。仅输出短枚举、减少帧数、不同推理后端或更大模型的效果和性能均未在本次验证，不能给出未经实测的加速承诺。

采样峰值：Instruct 进程 Metal driver memory 约 5.11–5.53 GiB，进程 RSS 约 2.19–2.66 GiB，系统可用内存最低约 4.34 GiB；交换内存约 18.86–22.27 GiB。RSS 与 Metal 内存口径重叠，不能相加或当作独立显存需求。原始采样在结果文件中。

## 数据与复现

- `model.json`：模型固定版本及本地缓存位置。
- `design.json` / `design-followup.json`：输入文件哈希、时间窗、标签、固定提示和参数。
- `results.json`：主测试、前 5 候选两轮重复、计时、原始输出和资源采样。
- `results-followup.json`：高像素预算、严格阴性、头部不可见和结构化观察补测。
- `summary.json` / `results-followup-summary.json`：按组汇总；标签以对应 design 的复核版本为准。
- `helmet-raw-segments.json` / `helmet-broad-candidates.json`：未阈值过滤的原片段排序与每视频候选。
- `production-baseline.json`：当前正式接口的候选和耗时。
- `review.json`：格式归一化后的结构化观察诊断及矛盾说明。

执行 `python experiments/instruct-verifier/summarize.py` 及 `python experiments/instruct-verifier/summarize.py results-followup.json` 可离线复算汇总。运行脚本拒绝覆盖现有结果；重新推理需指定新的输出文件。所有模型推理仅在本机进行，没有上传用户视频。

## 对当前项目的建议

可以继续研究“候选核验”，尤其对于场景与动作的组合；但目前不宜把这版 2B Instruct 直接作为默认自动过滤，更不能把输出当作可靠的未佩戴安全帽判断。

若进一步试验，应优先处理小头部的有效分辨率、同一人物的帽子归属、不可见状态，以及召回候选时间范围。更大的 Instruct 或专用安全帽检测器需要另外实测，本次没有测试 4B/8B，不能据此对所有 Qwen3-VL-Instruct 版本作结论。

本次未修改生产代码、页面或配置，服务 PID 未重启，仍是 40 个视频、129 个 Qwen 片段；两轮前后索引哈希与发布指针一致，见 `production-unchanged.json`。
