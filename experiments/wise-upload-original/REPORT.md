# WISE 原版上传索引离线对照

日期：2026-10-28（America/Los_Angeles）。主对比、上传回放、恢复后的实际查询核验均已完成。

## 判断

本批数据没有显示出将自然语言索引采样与编码整体切换成 WISE 原版的收益。64 条有答案查询中，正确视频排第一从 61 条变成 60 条，前五名包含正确视频从 64 条变成 63 条；41 个视频的 Qwen 解码与编码总耗时从 341.10 秒增加到 1183.10 秒，约为 3.47 倍。这个结论只适用于本机、本批视频和冻结查询，不能推断所有视频场景都会退化。

两条视频完整入库处理回放分别增加 30.3% 和 49.6%。建议现阶段保留当前上传方案：这批数据没有支持花费更多时间和内存整体切换。若继续研究，应分别控制采样、像素预算和精度，并扩充独立标注；不能仅因为“与原版一致”就预期检索更准。

“完全按原版”也不等于换了更强的模型：两边使用相同的 Qwen3-VL-Embedding 2B 权重，区别在采样、像素预算和 Mac 上的 FP32/FP16 精度。此次没有把这些因素逐项拆开，所以不能把任何改善或退化归因给某一个因素。

## 对照范围与依据

- 原版源码取自本地 WISE 上游提交 `fcfa443fbb46eb361bb19151339338616838a5b5`，从 Git 对象导出，不使用带本地补丁的编码器工作文件。导出文件及 SHA 见 `reference/`、`design.json`。
- A：当前 OpenCV 取帧，最长 8 秒、4 秒步长，每段固定 16 帧，FP16，总像素预算 1048576。
- B：原版 `VideoSegmentDataset` 与原版 Qwen 编码器，8 秒窗口、4 秒步长、2fps、最多 16 帧，按真实 PTS 记录边界，短视频较少帧、符合原版规则的短尾段不再独立编码；Mac 默认 FP32，总像素预算 7864320。查询向量仍用 A。
- C：视频索引同 B，文字查询也使用原版 FP32。
- 像素预算是上限，不代表每段实际像素都扩大 7.5 倍。例如首段实际模型输入从 980 token 增到 2004 token；1.4 秒短片的解码帧数从固定 16 帧变为 3 帧。逐段输入形状记录在各组 `result.json`。
- 三组均使用 WISE 原生向量搜索、最多 100 个候选片段和片段合并，再按视频保留最佳结果。无额外分数门槛、拆句或重排。
- 控制输入为现有 41 条已转码视频，总长 601.78 秒。**没有比较原始高分辨率上传文件直接编码与本项目 640 边长转码的差异**。上传回放保留本项目转码、OWLv2、人脸与项目复制步骤，仅替换 Qwen 部分，因此不是整套无定制 WISE CLI 的部署基准。
- 质量主表使用已有 40 视频、68 查询标注，其中 64 条有答案、4 条无答案。第 41 条未标注视频从主评分候选库排除，仅参加性能测试和附加诊断。未将未知样本强行当作负例。
- 标注来源为此前 **Codex 单次视觉核查**，不是独立双人标注。查看过全库时序图与部分细节，未遍历每个原视频帧。本次冻结并复用这些标注，没有依据新排名改标签。来源见 `../qwen8b-full-library/ANNOTATIONS.md` 和 `visual-review-notes.json`。
- 将片段级标注按视频取最高等级，完整相关（等级 2）计命中。以下指标是**视频检索指标，不是片段精确定位准确率**。

## 用户关心的复合条件

## 索引与搜索性能

硬件为 Apple M5、32 GiB 统一内存，macOS 26.5.1；具体运行库版本见 `environment.json`。模型均预加载后测视频/查询，冷启动另列；串行执行，没有两套 Qwen 同时推理。

测试时仍有其他桌面程序和系统交换内存，本次不是隔离服务器基准。原版测试过程可用内存最低约 2.81 GiB，未触发 2 GiB 连续低内存保护。数字不可直接外推到 NVIDIA GPU、其他精度或高并发服务。

| 阶段 | A 当前 | 原版 | 解释 |
| --- | ---: | ---: | --- |
| 全库 Qwen 解码与编码 | 341.10 秒 | 1183.10 秒 | 3.47 倍，增加约 247% |
| 生成片段数 | 135 | 134 | 尾段处理差异，所有 41 视频均有向量 |
| 特征文件写入 | 5.8 毫秒 | 32.5 毫秒 | 小样本、I/O 波动，不是主要耗时 |
| FAISS IndexFlatIP 建立 | 36.0 毫秒 | 43.3 毫秒 | 不含元数据复制 |
| 文字编码中位数 | 65.1 毫秒 | 104.1 毫秒 | 查询端也改 FP32 时约增加 38.9 毫秒，约 60% |
| 文字编码 P95 | 124.8 毫秒 | 153.3 毫秒 | 73 查询 × 3 轮，直接编码、绕过查询缓存 |
| 原生搜索与片段组织中位数 | 4.0 毫秒 | 4.0 毫秒（B） | 不含文字编码、缩略图发送、HTTP 与浏览器 |
| 模型加载（单次） | 8.02 秒 | 12.09 秒 | 文件缓存顺序不同，不能作为稳定冷启动结论 |
| Qwen 进程采样 MPS driver 峰值 | 5.17 GiB | 12.64 GiB | 两者是同一内存口径，不能再与 RSS 相加 |

因此，**仅换上传索引（B），本次没有观察到稳态搜索明显变慢**；连查询精度一起改（C），文字编码中位数增加约 39 毫秒。上述不是网页点击到首屏完成时间，也没有测 HTTP 并发。已核对正式纯文字入口走 WISE `EmbeddingService` 的直接编码；人物组合等其他链路的 ActionEngine 查询缓存不应套用到这里。

A 的首个原生搜索调用出现 1.91 秒初始化开销，B、C 已处于库函数热状态，不能用三组平均值判断搜索快慢；主表报告稳态中位数。没有从这条冷调用推断原版更快。

8 视频/23 段子集的当前方案首次 61.37 秒、同进程复测 63.74 秒，原版之后再起进程复测为 56.68 秒；原版同子集热复测 215.24 秒。系统状态有约一成波动，但不足以解释 3 倍以上的视频编码差距。后置当前文字编码中位数 57.3 毫秒，说明查询时间也应看作本机观测范围，不能承诺固定毫秒。

## 保护与复现

两轮测试均在 finally 自动恢复服务。最终 `/mvp/` 返回 200，Qwen 已加载，状态为 41 视频 / 135 片段。实际请求“骑自行车”“红色安全帽骑自行车”“红色安全帽写字”，分别返回 34、35、32 个视频，完整视频排序均与当前方案离线基线一致。见 `restored-service-check.json`。

正式保护清单共 86 个文件，最终哈希均未变，活动发布指针和 41 个视频源文件均未变；没有改正式页面、配置、索引及人脸库。当前生产片段与本次重建基线形状和元数据一致，向量最大绝对误差为 0，验证了基线代表当前正式实现。回放的可丢弃工作目录已清理。

结果文件：`summary.json` 为汇总，`query-comparison.csv` 为查询摘要，`query-results.json` 为 A/B/C 完整排名，`current-full/`、`original-full/`、`current-check/` 保存原始测速。`upload-summary.json` 汇总上传，`replays/*/result.json` 保存各阶段计时。`production-after.json` 为保护文件及活动指针审计，`suite.json`、`replay-suite.json` 记录恢复状态。

从仓库根目录加载 `scripts/env.sh` 后运行实验脚本。`prepare` 会冻结状态，已冻结目录不得覆盖；`suite` 需要停服授权，内部 finally 恢复服务。`evaluate.py` 只操作实验内的 WISE 项目副本。原版回放只构建原生 Qwen 索引，未实现当前人物组合检索依赖的 action snapshot 兼容，因此这些脚本不是可直接发布的替换实现。
