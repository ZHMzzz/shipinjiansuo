# 批量 1/2 的性能定位（2026-10-28）

本轮完成了固定输入交错计时、模块插桩、PyTorch MPS 算子/拷贝/回退统计，以及独立算子复测。正式代码和活动索引均未修改。

结论：Qwen 已找到可复现的额外开销及限制合批收益的实现细节；OWLv2 尚未锁定单一慢算子。上轮完整样本的批量 2 无提速结论保留，但不能把上轮 +7.5% 当成 OWLv2 在所有执行方式下的固定惩罚。另发现 Qwen 图像块投影是值得优先验证的优化点。

## 实验方法与工具边界

- 本机 `xcrun --find xctrace` 返回不可用，未安装 Xcode，也没有录制 Instruments GPU 时间线或硬件带宽计数器。
- 验证并使用当前 PyTorch 2.8 的内置 MPS 日志：`PYTORCH_MPS_LOG_PROFILE_INFO=392`（统计及 GPU/调度时间）。独立算子统计进程另设 `PYTORCH_MPS_TRACE_SIGNPOSTS=4`，逐操作提交并等待，减少多个算子共用同一 command buffer 导致的重复时间归因。
- 强制等待会改变调度，MPS 统计用于识别操作及线索，**不作为线上吞吐数据，不把各条 GPU 时间相加当总耗时**。共享 Metal kernel 的统计名称可能仅包含最后一次形状；完整输入形状和调用次数另由 CPU dispatch trace 验证。
- CPU profiler 只用于输入形状、调用次数和主机调度，不把 `self_cpu_time` 解释为 GPU 算子执行时间。
- 固定原样本中的视频 1 和 40，各取两帧或两个原有 Qwen 片段。视频内容哈希检查通过；解码放在计时外，模型权重只加载一次，批量 1 和 2 都先预热。
- 阶段测试按 `1,2,2,1,2,1,1,2` 交错，每条记录处理相同的四帧或四片段。每阶段前后同步 MPS，单独记录预处理、搬运、模型和后处理。两种批量输出逐元素一致。
- 细模块插桩、粗模块插桩及 MPS 逐算子统计分别运行，不把带插桩的总时间当作原生性能。模块时间存在包含关系，例如 visual_total 包含 visual_attention，不可相加。

## 1. 预处理、传输及 CPU 回退不是本轮主要慢点

以下是阶段测试均值，每行均处理同样四个输入；单位秒。

| 阶段 | OWLv2 批量 1 | OWLv2 批量 2 | Qwen 批量 1 | Qwen 批量 2 |
|---|---:|---:|---:|---:|
| CPU 预处理 | 0.0281 | 0.0286 | 0.3082 | 0.2763 |
| 输入搬到 MPS | 0.0040 | 0.0032 | 0.0129 | 0.0068 |
| 模型计算阶段 | 1.1555 | 1.2076 | 9.0660 | 9.3501 |
| 输出搬回 CPU | 0.0038 | 0.0027 | 0.0011 | 0.0005 |

两种模型在此阶段测量中，差异主要出现在模型阶段。四份 MPS 日志（两模型 × 两种批量）均报告没有 CPU fallback。MPS 拷贝统计包含模型权重加载，因此不能把其中约 4 GiB 的 Qwen CPU→MPS 拷贝全部算作每次片段编码的开销。

## 2. Qwen：限制收益的实际执行路径与可复现慢点

实际运行配置确认视觉和文本 attention 都为 `sdpa`。CPU dispatch trace 显示，处理同样两个片段时：

| 调用 | 批量 1 | 批量 2 |
|---|---:|---:|
| 视觉 SDPA，形状 `[1,16,448,64]` | 384 次 | 384 次 |
| 文本 SDPA | 56 次，batch=1 | 28 次，batch=2 |
| 图像块 Conv3d | 2 次，3584 个 patch/次 | 1 次，7168 个 patch/次 |

因此外部片段合批没有减少视觉 attention 的调用次数。视觉实现内部仍按块逐个计算；文本部分虽减少调用次数，但每次计算量增加。单片段的图像块投影本来已经一次处理 3584 个 patch，不能把“片段 batch=1”理解为模型内部只处理一个小单元。

独立复测捕获真实首层视觉 RoPE 输入（形状 `[7168,16,64]`、stride `[1024,64,1]`），比较拆成两半执行与整块执行。八次交错测试，中位数如下，均完成同样两个片段对应的工作：

| 操作 | 分开执行 | 合并执行 | 观察 |
|---|---:|---:|---|
| `rotate_half` | 5.419 ms | 6.808 ms | 合并约慢 25.6% |
| 其中非连续切片的 `neg` | 3.306 ms | 5.736 ms | 合并约慢 73.5% |

这是一个在同输入、同设备下复现的变慢点。该操作在视觉层中对 Q、K 反复执行，会累积开销。但不能把孤立算子的差值直接乘调用次数，宣称精确解释了整个模型的 4.5%；调度、缓存和周围操作都会改变表现。未采集带宽计数器，不能把它进一步断言为“内存带宽已打满”。

## 3. OWLv2：没有证据支持某个注意力算子必然变慢

真实 dispatch trace 的注意力矩阵从 `[12,3601,3601]` 变为 `[24,3601,3601]`。仅一个 FP16 矩阵的理论数据大小就从约 297 MiB 增至约 594 MiB，合批没有减少计算量或这些中间数据。上轮实测 MPS driver 峰值增长有明确的张量规模背景。

但独立暖态 `QKᵀ → softmax → AV` 测试，处理两帧的中位数是 **32.31 → 31.31 ms**，批量 2 反而略快。另一个预处理输入已驻留 MPS、仅运行整个模型且不加模块钩子的测试是 **1.1661 → 1.1487 秒**（四帧），也只有约 1.5% 的差异。

粗模块同步插桩后，视觉骨干约 **1.1416 → 1.1642 秒**，整个模型约 **1.1688 → 1.1860 秒**；而细层级插桩也会改变比较方向。分类、物体和框预测头各只有几毫秒，不是主要时间来源。

这些结果说明 OWLv2 的小幅差异依赖执行边界、输入驻留、缓存及系统状态。可以确认主要时间花在视觉骨干，并且批量 2 增加内存占用；**还不能确定单一算子或带宽瓶颈是上轮 +7.5% 的根因**。此前“更大中间张量可能降低效率”仍是解释线索，而不是已经证实的硬件结论。

## 4. 新发现：Qwen 图像块 Conv3d 值得单独优化

在真实像素输入和 FP16 权重上，图像块投影的 Conv3d 完成两个片段对应的工作，中位数约 **1.535 秒（分开）/1.527 秒（合批）**；合批基本没有改善。这是明显的时间消耗点。

该层每个输入 patch 恰好为 `3×2×16×16`，卷积核和步长都是 `2×16×16`，输出空间为 `1×1×1`。因此可在数学上表示为对 1536 维 patch 的线性映射，复用完全相同的权重和 bias。

隔离算子试验中，同权重 `F.linear` 耗时约 **2.325 ms / 2.131 ms**。这不是完整索引提速，不能宣传整个索引快几百倍。FP16 输出存在差异：

- 最大绝对差：0.00390625；平均绝对差：0.0000348328。
- 相对 L2 误差：0.0002602，约 0.026%。
- 原始 Conv3d 的两种批量输出仍逐元素一致。

该替换仅存在于隔离算子脚本，没有改正式模型，也没有完成替换后的全片段向量与检索回归。下一项最值得验证的是这个投影替换的整段编码收益及检索稳定性；继续单纯增大片段批量的优先级较低。

## 文件、复现与完整性

在仓库根目录，使用新的输出路径，两模型始终串行：

```zsh
source scripts/env.sh
export MICROPROFILE_OUT="$PWD/experiments/indexing-optimization/microbatch-profile-retest-01"
python experiments/indexing-optimization/profile_microbatch.py suite
python experiments/indexing-optimization/profile_kernels.py owl
python experiments/indexing-optimization/profile_kernels.py qwen
python experiments/indexing-optimization/profile_owl_coarse.py
```

结果位于 `microbatch-profile-20261028/`：

- `owl-stages.json`、`qwen-stages.json`：各阶段、模块、运行配置和 CPU dispatch 数据。
- `*-mps-b*.log`：真实 PyTorch MPS 算子、拷贝和回退统计。
- `*-cpu-dispatch-b*.json`：Chrome trace，仅包含 CPU 侧事件。
- `owl-kernels.json`、`qwen-kernels.json`、`owl-coarse.json`：独立复测。
- `summary.json`：汇总；`final-integrity.json`：正式指针、项目文件、人脸登记库及正式脚本/模型源码内容指纹一致。

参考实现：[PyTorch 2.8 MPS profiler 源码](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/mps/MPSProfiler.mm)、[MPS 工具与 profiler 文档](https://docs.pytorch.org/docs/2.8/mps.html)。模型执行路径以本机实际安装的 Transformers 实现和本轮运行 trace 为准。
