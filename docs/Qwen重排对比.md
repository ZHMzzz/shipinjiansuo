# Qwen 动作片段重排对比

## 使用方法

打开 http://127.0.0.1:9670/mvp/ → 07 动作片段 → 输入中文 → 勾选“启用 Qwen 重排对比”。默认前 10 个候选，可选 5、10、20 段。查询完成后点“原始排序 / 重排排序”，在同一批候选上比较；切换排序不会再推理。每张卡片保留原排名、向量相似度、重排分，点击从该候选的起点播放。

不勾选时仍走原动作向量检索。勾选后只展示选定候选集，不把未评分的其他结果与重排分混排。模型或解码失败时明确标出“重排未完成，当前显示原始排序”，不应用部分重排结果。

## 来源与实现

这部分是本项目扩展，WISE 2 上游未集成 Reranker。使用 [Qwen 官方模型](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B)，固定模型版本 `4bd860ac4f15ad1897a214615cccc700f8f71818`。模型权重约 4.26 GB，Apache-2.0。

`scripts/action_reranker.py` 参考该模型版本的 [官方 Transformers 代码](https://huggingface.co/Qwen/Qwen3-VL-Reranker-2B/blob/4bd860ac4f15ad1897a214615cccc700f8f71818/scripts/qwen3_vl_reranker.py) 适配：保留官方 system prompt、Instruct/Query/Document 格式及 yes/no 打分方式。视觉主干和语言主干联合处理中文查询与候选视频，取最后 token 的隐藏状态，投影到 `yes` 与 `no` 输出权重差，经过 sigmoid 得到排序分。FP32 投影用于减少半精度累加误差；主干仍为 FP16。

M5 上使用 MPS，逐个候选推理。每个候选在原起止范围内均匀取 16 帧，总像素预算 1,048,576；解码后单帧先等比例限制在 1024×1024 内，再由 Qwen 处理器缩放。全部帧作为一个视频输入。**没有把文件名、人工标签或 Embedding 分数交给模型。** 解码失败直接报错，不沿用官方示例中的 NULL 替代输入。

流程：

```text
中文 → Qwen Embedding 查询向量 → FAISS 召回 → 原有重叠片段去重 → 前 N 个候选
                                                            ↓
                         查询文字 + 每个候选的 16 帧 → Qwen Reranker → 按重排分排序
```

上传流程和现有索引没有增加模型或重建任务。重排读取当前索引所对应的原视频，因此以后新入库的视频也可以参与重排。它只能重新排列已召回候选，不能找回候选集以外的片段。

## 内存和耗时口径

Embedding 与 Reranker 轮流驻留；载入 Embedding 前释放 Reranker，重排前释放 Embedding，均保留现有索引。最近 64 条查询的文本向量缓存于内存，缓存不随重启保留，且与视频库版本无关；视频候选和重排分不缓存。

同一描述再次重排可以跳过模型切换。切换到未缓存的新描述时需要重新载入两个模型，不能把这种查询与重复查询的速度混为一谈。若上传建立动作索引，后续重排也可能重新载入模型。

API `/mvp-api/actions/search` 增加表单字段 `rerank`（默认 false）与 `rerank_candidates`（1–20，默认 10）。响应保留原结构，另有 `baseline_results`、`rerank`、`retrieval_seconds`、`query_embedding_cached` 和 `resources`。原 `distance` 始终是向量相似度，重排分单独放 `rerank_score`。

资源每 50ms 采样：当前服务进程 RSS、MPS 活跃张量、Metal 驱动分配量、系统可用内存和系统 swap。RSS 与 MPS 内存有重叠，不能相加；这是采样峰值，不是精确硬件峰值。系统 swap 包含其他应用和以前累积的交换，不能全部归因于此次检索。API 耗时从服务开始处理到完成，不包含排队与 HTTP 传输；实测脚本另记 HTTP 总耗时。

## 复现

```sh
source scripts/env.sh

python -m pytest -q tests

```

最后一项在运行中的 Demo 上，对未戴安全帽、戴安全帽、翻越围栏、摔倒分别执行原始、重复原始、首次重排、重复重排，保存 `experiments/reranker/live.json`。

另有固定 10 短片对照：先停止 Demo，再执行 `python scripts/benchmark_reranker.py --fixture`，结束后启动 Demo。此项核对样本 SHA256，沿用此前 `qwen-fp16.json` 的 Embedding 排名，对完全相同的候选重新打分，保存 `fixture.json`；它的内存属于独立测试进程，不能当作在线服务总内存。

## 效果解释

未戴安全帽必须同时满足人物、头部可见性与佩戴状态。重排分是相关性，不是“未戴安全帽”的校准概率；没有新增安全帽检测框、逐人头部关联或未知状态分类。现有固定样本包含两段来自同一仓库的裸头画面，与三段安全帽施工画面，场景并不严格配对，不用于证明课题验收准确率。

## 本机在线实测（2026-10-27）

Apple M5 / 32 GiB，MPS FP16，当前 26 视频 / 70 片段。原始响应和逐候选耗时保存于 `experiments/reranker/live.json`；它记录固定发布版本，测试期间未变更视频库。

| 查询 | 原始检索，含切换/加载 | 同句重复原始（向量已缓存） | 首次重排 10 段 | 重复重排 10 段 |
|---|---:|---:|---:|---:|
| 作业人员没有佩戴安全帽 | 9.79 秒 | 0.007 秒 | 32.95 秒 | 26.57 秒 |
| 工人佩戴安全帽 | 8.02 秒 | 0.005 秒 | 29.94 秒 | 23.14 秒 |
| 人员翻越围栏 | 5.86 秒 | 0.002 秒 | 28.45 秒 | 25.33 秒 |
| 一个人失去平衡摔倒在地 | 6.86 秒 | 0.007 秒 | 34.52 秒 | 25.78 秒 |

以上为 HTTP 耗时。每一行原始检索之后，再开启重排，所以“首次重排”复用了该查询向量，只额外加载 Reranker；全新描述直接开启重排还要承担 Embedding 加载/编码时间。“重复原始”的毫秒数只是缓存命中，不能当成新查询编码速度。

为补充未缓存的新描述性能，服务恢复后又测了三个不同查询：第一次加载耗时 8.13 秒，随后模型驻留时两个新描述分别为 0.092 和 0.112 秒，均未命中文本向量缓存。详见 `warm-new-queries.json`。

同一条“作业人员没有佩戴安全帽”、Reranker 已加载：前 5 段 11.95 秒、前 10 段 26.57 秒、前 20 段 48.79 秒。5/20 段原始响应另存 `candidate-counts.json`。10 段结果来自上一轮重复查询，非同时运行；这只是本机少量实测，非统计性能保证。

10 段重排期间整个服务进程的 Metal 驱动采样峰值约 6.57–7.64 GiB，RSS 采样峰值约 0.73–0.97 GiB；两者口径不同且重叠。包括前置原始检索加载在内，整组请求最高 RSS 约 5.20 GiB、最高 Metal 驱动约 8.21 GiB。系统可用内存最低约 4.34 GiB，未触发 2 GiB 内存保护。macOS 的压缩与交换会影响这些读数，不能把低 RSS 解读为模型只占不到 1 GiB。

### 安全帽结果

当前库查询“作业人员没有佩戴安全帽”，原始第 5 名的仓库裸头片段（视频 17 的 16–24 秒）重排后第 6 名；原本位于前列的戴帽工地/仓库画面仍在前列。因此这轮**没有解决否定条件误检**。重排并不保证每条查询都改善。

“人员翻越围栏”对应的金属围栏短片仍为第一名。摔倒查询的重排结果第一名变成串接样本的 12–20 秒窗口，该窗口混有背包行走与摔倒内容，不能把排序变化等同于更精准的动作起止定位。

同时用固定版本官方参考 `process()` 对同一 `helmet_outdoor` 输入核对：官方分数 0.50048828，本地 0.50040632，绝对差约 0.00008196，低于 0.002 容差。本地投影使用 FP32，参考使用 FP16；这是一个输入上的适配一致性检查，不是完整数值等价证明。参考源码、来源 URL 与 SHA256 保存在 `experiments/reranker/reference/`。模型权重 SHA256 与下载的 LFS 对象一致，记录于 `model-provenance.json`。

本项目 `tests/` 的 30 项测试通过，包括关闭重排时不调用模型、失败保留原始结果、分数非法拒绝、候选身份与时间不变、文本向量缓存边界等。原有四类检索、组合查询、动作时间定位及 HTTP 视频范围播放的实际接口回归通过。

浏览器实际查询、原始/重排排序切换及 16–24 秒片段播放通过，截图见 `experiments/reranker/demo-comparison.png`。测试前后的发布指针与动作索引文件 SHA256 一致（`index-before.json`、`index-after.json`），服务已恢复。
